# 跨包元教训（Meta Lessons）

> **来源**：v1.5.2 → v1.7.1 累计 8 个跨包可复用教训（每条注明发源实例）
> **维护**：随包分发，引用即归因；新教训增补时追加末尾 + 更新版本号
> **使用场景**：任何 Team 型专家包评审、v2+ 路线图决策、跨包推广

---

## ML-1「两层拼合处静默失效」家族

**现象**：A 系统与 B 系统通过接口/触发词/协议衔接时，A 单独测试通过、B 单独测试通过，但 A+B 拼合处静默失效——不报错、不告警、只不工作。

**已识别 3 实例**：

1. **C1 Mode 2 触发词空缺**：coding-prompt Mode 1 触发词是「用户与 AI 交互」场景（`优化提示词: ...`/`激活编程提示词`），但在「主理人 spawn 独立 agent 下发任务」场景下永不出现，导致 Mode 2 监控 0 运行
2. **阶段一 N2** `replace` 空转：检查器用 `text.replace(target, replacement)`，当 target 文案在 P0 期间被改成另一种说法后，`replace` 静默不报错 → 假绿通过 CI
3. **1.6.0 N1 mkdir EEXIST**：`Path.mkdir(exist_ok=True)` 对已存在路径仍走沙箱 broker 拦截 → 报 PermissionError(EEXIST)，但目录实际已存在，第二次跑就崩

**统一处置范式**：

- **不要只测单边**——必须做「A 真实使用 B」/「B 真实接收 A」的端到端测试
- **拼合处两侧各加护栏**：A 在不期望时显式拒绝而非默不作声；B 接收 A 时校验
- **不能假设 `ex_ok=True` / 默认值 / 触发词**——这些是「最不显眼的设计假设」，最易随时间漂移

## ML-2「自进化」最低门槛不是 PK 表，是闭合回路

**现象**：v1.6.0 落地 learnings.md + 6 列 Pattern-Key 跟踪表 + 4 步采集协议。但「自进化」要真正运转需要 ① 真实任务跑过 P0-P3 4 阶段 ② coder/tester 实际附 `candidates: [PK-...]` 字段 ③ 主理人阶段收尾合并 ④ PK 复现 ≥2 晋升 promoted ⑤ promoted 反哺 P0/P1 优化候选。这条**闭合回路**缺一不可，缺了 PK 表就是空模板。

**已识别实例**：v1.6.0 learnings.md 落 PK 表后到 v1.7.1 仍 0 条目——因为没有真实任务跑通过 4 阶段

**处置范式**：

- PK 表 + 采集协议 = 机制就绪
- 真实任务数据 = 机制激活
- **机制就绪 ≠ 机制运转**——评审时必须问「自进化跑出过 PK 数据吗？没跑过就是装饰」

## ML-3「质检 ≠ 通过」（自证循环陷阱）

**现象**：自检型测试 = 「P0 验证」+「同一组 fixture 的回归」= 7/7 PASS = 「看起来好」。但这是「自证循环」——你用一组 fixture 验证门禁 + 门禁对同组 fixture 100% PASS = 没有外部信号证明门禁真的能挡坏样本。

**已识别实例**：

- v1.6.0 evals 7 fixtures 全是 P0-3c 加固时定义的验收锚点——门禁对自检样本 100% 通过
- v1.7 加 6 generated 样本——同源变异（关键词与门禁同源），仍是自证
- **直到 v1.7.1 加 viral-evo-lab 真实样本**：4/43 覆盖 exit=1，**暴露了 H 框架模板与真实世界设计的结构性 gap**——这才是 evals 真正起作用

**处置范式**：

- 自检 fixture 是「保底」不是「证明」
- **必须从历史项目抽真实样本**（与门禁同源程度低），即便 FAIL 也是有价值的——暴露门禁 vs 真实世界偏差
- 真实样本征集 = 用户授权 + 匿名化流程，不是技术问题

## ML-4「默认假绿」是门禁文化问题

**现象**：单脚本「`if X and args.strict: return 1`，否则 return 0」模式是常见写法，但**调用方忘传 `--strict` 就恒定假绿**。单点假绿可忍，系统性默认 0 = 包对「忘传参」零容忍——所有「if X and --strict: return 1」必须反转。

**已识别实例**：

- v1.5.2 baseline 两个校验器（check_design_doc.py + lint_knowledge.py）都中招
- v1.6.0 P0-3 反转后用 7 组变异测试杀红 + 3 对抗攻击全挡

**处置范式**：

- 默认严格（strict by default） + 显式放行（`--lenient`）
- **不要把严格当作可选项**——可选项是「使用者会忘」的同义词
- 校验器测试必须含「忘传参」场景，并断言退出码 1

## ML-5「校验器 vs 模板」必须同源

**现象**：模板（`assets/design-doc.md`）与校验器（`check_design_doc.py`）独立维护时，模板提示的「问什么」与校验器检查的「答什么」会漂移——架构师按模板认真填，门禁判「关键词未覆盖」。

**已识别实例**：

- v1.5.2 baseline：模板 §4.1-§4.6 提示词漏掉多数必答问题（E3/E7、C3/C6、S2/S3、L2/L3/L6、V2/V4/V6/V7），按模板填的文档 41/43 覆盖
- v1.6.0 P0-3b 扩模板 + 改 MIN_LINE_CHARS=20 → 43/43 模板填满

**处置范式**：

- 模板与校验器是同一份事的两个面——改一边必改另一边
- **生成器也从校验器解析关键词**（不硬编码）——v1.7 P3-8 generate_samples.py 用 `re.search` 直接从 `check_design_doc.QUESTION_KEYWORDS` 解析，确保同源
- 「模板同源校验器」测试：跑校验器对模板填满的样本，必须 ≥N/N 覆盖

## ML-6「知识仲裁孤岛」三类：规则-执行-可见性脱节

**现象**：知识使用规则（policy.md 写「团队语境下不用外部库」）+ 工具执行（knowledge_lib.py 仍接受 ingest）+ 主理人可见性（team-lead §八 不引用该规则）三方脱节——规则存在但无执行约束、无可见性提示。

**已识别实例**：

- v1.5.2 baseline：knowledge-policy.md L7/L17 有仲裁「团队语境下不用 knowledge_lib」「写读位置必须同一套」（自述历史踩坑所立），但 team-lead §八 不引用、knowledge_lib.py 团队语境下无警告
- v1.6.0 P1-3 修复：team-lead §八 显式引用 + policy 双向锚定 + knowledge_lib 团队模式警告

**处置范式**：

- 仲裁规则必须**显式在主理人层可见**（不是埋在技能文档里）
- 工具必须在**「不该用的场景」显式拒绝或警告**（不是默默执行）
- 任意一方脱节，仲裁失效

## ML-7「撞限协议下沉成员」覆盖率必须 4/4

**现象**：「撞限协议」只在主理人层定义，调度成员时「随任务下发本协议」——但实际执行时主理人调度指令天然不含该段落（任务下发是需求声明，不是协议同步）。4 成员在独立 agent 上下文里 0 覆盖，撞限行为完全靠主理人记得复述。

**已识别实例**：v1.5.2 baseline 撞限协议只在 team-lead L42/L210，4 成员 MD 全 0 命中。v1.6.0 P1-1 修复：协议全文下沉到各成员 MD「撞限协议（内置）」节，成员自启动即知协议

**处置范式**：

- **协议下沉到成员**比「主理人随任务下发」更可靠——主理人会忘，协议不会
- 覆盖率检测：`grep '协议关键字' agents/*.md` 应该在 5 个文件（4 成员 + team-lead）都命中
- 任何「主理人下发时随附」类协议都该下沉到成员

## ML-8「主理人亲做小颗粒 vs worker 并行」取舍（token 限额下）

**现象**：4 worker 并行 13 分钟触 token 限额（429）；主理人单 worker 改少量文件 13 分钟成功。看起来「写大做广」反而是劣势。

**已识别实例**：

- v1.6.0 P1 4 worker 并行 13 分钟：3 个 429 失败（虽然失败前 commit 已落盘）
- v1.6.0 P2 + P3：主理人亲做 1-2 文件 13 分钟，全部成功

**处置范式**：

- **write-heavy 任务不并发同文件**（避免 working tree 互踩，v1.7 落地「并发 working tree 接力」现象即此病）
- 颗粒小（1-2 文件 + 1 commit）+ 任务独立（不冲突）= 并发有效
- 颗粒大或多文件改一处 = 主理人亲做更稳
- **每个 commit 原子三步**（restore --staged + add + commit）能避开大多数并发互踩

---

## ML-9「并发 working tree 接力」现象（v1.7 落地新发现）

**现象**：多个 worker 同时改同一仓库时，working tree 互踩——A worker Edit 完一个文件，git add，B worker 同时 Edit 同一文件，git add。B commit 时连带把 A 的改动 commit 进 B 的 commit 信息（commit message 写 A 任务但包含 B 改动）。或 A commit 时 B 的改动被 git restore --staged 回退几次。

**已识别实例**：

- v1.7 P3 阶段 4 worker 并行：P3-5 worker 报告 P3-1/2/7 worker 反复 restore 其 staging，过程中 P3-5 在 _handoff_schema.md 的 +1 行被回退几次
- P3-7 commit (`1612bbd`) 连带提交 P3-5 worker 在 working tree 未提交的内容——「working tree 接力」

**处置范式**：

- **每个 commit 原子三步**（restore --staged + add + commit）干净——失败可重试
- 透明化：commit message 显式声明「连带提交其他 worker 在 working tree 的内容」
- 替代「worker 间加锁」破坏并发收益
- 主理人收尾时检查 commit 链是否完整（每个任务 commit hash 是否存在、working tree 是否干净）

## 跨包使用指南

任何 Team 型专家包评审时：

1. **按 ML-1 拼合处审计**——「A 单独测试通过 + B 单独测试通过，A+B 端到端测试通过吗？」
2. **按 ML-2 自进化审计**——「自进化 PK 数据出现过吗？没出现过 = 装饰」
3. **按 ML-3 真实样本审计**——「evals 全是 fixture + generated 还是有真实样本？真实样本 FAIL 几次？偏差是否被讨论？」
4. **按 ML-4 默认假绿审计**——「所有校验器默认 strict 还是默认 0？忘传参测试覆盖吗？」
5. **按 ML-5 同源审计**——「模板与校验器是同一份事吗？修改一边另一边会同步吗？」
6. **按 ML-6 仲裁孤岛审计**——「知识使用规则在主理人层可见吗？工具在不该用时显式拒绝吗？」
7. **按 ML-7 协议下沉审计**——「关键协议在 4 成员 MD 都覆盖吗？」
8. **按 ML-8 派工策略审计**——「本次 write-heavy 任务颗粒小吗？worker 间文件不冲突吗？」
9. **按 ML-9 并发 commit 审计**——「每个 commit 原子三步执行吗？commit message 透明化连带吗？」
