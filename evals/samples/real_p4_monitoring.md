# P4 预研：慢通道监控架构升级设计（2026-10-14）

> 定位：专家团内部架构预研文档（非项目资产）。回答一个问题：
> **5+ 成员并行 spawn 时，主理人如何从"轮询 poll"进化为"事件驱动"？**
> 边界：只做设计与选型分析，不落地实现（实现列入 backlog，见 §5）。

---

## 1. 现状与痛点

### 1.1 当前监控机制
- 主理人 spawn 成员后，用 **TaskOutput 轮询**（block=true 等完成 / block=false 查状态）
- 信封双通道：成员落盘 artifact（主通道）+ SendMessage 摘要（辅通道）
- 撞限协议依赖成员主动上报

### 1.2 实测痛点（本会话观察）
| 现象 | 根因 |
|---|---|
| 4.5h 内 429 限流 ×4，无自动降级 | 轮询间隔固定，限流时仍按原节奏重试 |
| 多成员并行时主理人上下文被"等待输出"占满 | block=true 同步阻塞，无法并行推进其他阶段 |
| "产出落盘了但 envelope 没回"无法区分 | 双通道无关联校验，主理人无法 5 秒判定是哪一半失败 |
| 成员轮次耗尽（撞限）只能被动等通知 | 无主动探测机制 |

### 1.3 约束（不可违反）
1. 平台机制优先：TeamCreate/Agent/SendMessage/TaskOutput 是平台给的，不自建消息总线
2. 确定性工程边界：**监控=结构性检查**（artifact 是否存在/envelope 是否落盘）属确定性，可脚本化；"产出质量如何"仍是 LLM 判断
4. 成员不直连：所有信息流经主理人（中转铁律）

---

## 2. 候选方案分析

### 方案 A：TaskOutput 周期化（最小改动）
- 做法：block=false + 固定间隔轮询，主理人自行管理节奏
- 优点：零新组件；缺点：仍是轮询，限流/上下文占用无改善
- **评估：❌ 不解决问题**

### 方案 B：落盘契约 + 确定性巡检脚本（推荐）
- 做法：成员产出**必须**落盘 `<run-dir>/<task-id>__<member>.md`（既有契约）；
  新增 `scripts/poll_run_dir.py <run-dir>`——**纯确定性**：列出
  ①期望成员清单（从 task 下发记录）②实际落盘文件 ③缺失/超时清单
- 监控循环：主理人每个阶段节点跑一次 poll_run_dir（秒级），替代 TaskOutput 阻塞等待
- 与现有机制关系：**不替代 SendMessage**（消息仍是成员→主理人的语义通道），
  poll 只回答"文件到了吗"这个结构问题；TaskOutput 保留作为兜底
- 优点：①主理人上下文零占用（脚本输出 3 行）②限流时巡检间隔可自适应
  ③"落盘 vs 回传"失败可定位（文件在=成员完成；文件不在=未完成/撞限）
- 缺点：多一个脚本；期望成员清单需主理人维护（可从 spawn 记录自动生成）
- **评估：✅ 核心推荐**

### 方案 C：消息驱动（SendMessage 主动通知）
- 做法：成员完成即 SendMessage，主理人收到即处理（平台本身支持）
- 优点：真事件驱动；缺点：消息丢失风险（实测仅消息回传曾丢失——
  这正是双通道契约存在的原因），且无法回答"还没回的是在干活还是撞限"
- **评估：🟡 作为 B 的语义补充，不作主监控**

### 方案 D：外部编排（cron/CI 定时巡检）
- 做法：cron 跑 poll_run_dir.py，超时告警
- 优点：主理人不在线也能推进；缺点：跨会话状态同步复杂，本团暂不需要
- **评估：⏸ 列入远期 backlog**

## 3. 推荐架构（B+C 混合）

```
                 ┌─────────────────────────────┐
                 │ 主理人（编排层）              │
                 │  - 阶段调度 / 门禁 / 中转     │
                 └──────┬──────────────────────┘
        下发 task_payload │ ▲ envelope(SendMessage 语义通道)
                          ▼ │
                 ┌─────────────────────────────┐
                 │ 成员（隔离执行）              │
                 │  产出 → Write artifact(主通道)│
                 └──────┬──────────────────────┘
                        │ 落盘
                        ▼
              <run-dir>/<task-id>__<member>.md
                        │
              poll_run_dir.py（确定性巡检：秒级、上下文零占用）
                        │
              期望清单 vs 实际落盘 → 缺失/超时/撞限清单
                        │
              主理人据清单决策：等待/催办/降级/终审
```

**关键设计**：
1. **双通道职责分离**：artifact=真相（结构），SendMessage=意图（语义）
2. **巡检脚本只做结构判断**：文件在/不在/超时——不含任何质量判断（LLM 领域）
3. **超时阈值分级**：单成员默认 T+15min 未落盘=黄（可能撞限），T+30min=红（上报管家节点）
4. **429 自适应**：巡检遇限流时间隔 ×2（指数退避），不硬闯

## 4. 与既有机制的兼容性

| 既有机制 | 兼容性 |
|---|---|
| 信封契约（6 字段） | ✅ 不变；poll 不读 envelope 内容，只查文件存在 |
| 双通道契约 | ✅ 强化：artifact 从"主通道"升级为"监控事实源" |
| 纪律审判 T0/T1 | ✅ T1 收 envelope 后先跑 poll 确认无缺失成员，再跑 verify_member_output |
| 撞限协议 | ✅ 强化：poll 的红名单直接触发撞限上报（不再等成员自报） |
| 中转铁律 | ✅ poll 脚本输出只给主理人 |

## 6. 结论

**轮询进化的方向不是"更聪明的轮询"，而是"把结构判断交给确定性脚本，把语义判断留给 LLM"**。
方案 B+C 用最小改动（1 个脚本 + 1 行 spawn 记录 + MD 三步）实现：
- 主理人上下文占用：从"等输出"变为"3 行巡检报告"
- 失败定位：从"猜"变为"文件在/不在"二值判定
- 撞限发现：从"被动等"变为"超时红名单主动触发"
