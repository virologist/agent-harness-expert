## 6. 结构智慧

关于何时修补 vs 重写，以及如何思考架构。

### 6.1 修补 vs 重写决策

| 信号 | 行动 |
|------|------|
| 改过 1-2 次，每次都有明确改进 | 继续迭代 |
| 改过 3+ 次，只有边际改进 | 停。考虑重写。 |
| 修复开始引入新复杂度来迁就旧设计 | 重写。旧架构里长出的新复杂度是死胡同。 |
| 根本设计假设错了 | 立即重写。不要犹豫。 |

**经验法则**：同一问题最多打 2 次补丁。第 3 次就重新设计。

### 6.2 局部优化陷阱

反复打磨细节却不满意，通常说明**架构错了**。

**诊断信号**：同一模块改了 3+ 次没解决；每次修复只是「缓解」从未「解决」；方案越来越复杂。

**应对**：停止打补丁。从使用场景重新分析。真正的问题通常在你正在看的层级的上一层。

### 6.3 级联验证

任何修改后，验证的不只是「改的部分能用」，还有「没改的部分仍然能用」。AI 可能悄悄改动依赖链或删除被间接引用的代码。

**规则**：改动后额外检查：
1. 被改模块的所有调用方仍然正常
2. 被删除的代码/import 没有残留引用
3. 核心流程端到端测试通过

### 6.4 彻底清理

功能完全移除且无需向后兼容时，删干净——半清理比不清理更糟。未来的维护者分不清什么是「故意留的」、什么是「忘了删的」。

**搜索范围**：函数名、import 语句、引用旧设计的注释、文档示例、其他方法里的条件分支。

### 6.5 映射/转换逻辑的冲突测试

任何涉及命名规则、key 生成、哈希或序列化的设计，必须在**设计阶段**包含冲突测试——不是测试阶段。

**规则**：设计任何映射/转换规则时，构造边界用例：
- 特殊字符（点、下划线、空格、中日韩文字）
- 语义等价输入（`a.b` vs `a_b`）
- 极端情况（空值、超长输入、深层嵌套）

发现冲突风险就在设计里解决。不要等测试阶段。
