## 4. 工作流模板

覆盖功能开发全生命周期：启动 → 对齐 → 纠偏 → 推进 → 验证 → 审查 → 调试 → 走查 → 交付。直接使用或按需改编。
弱 → 强转换示例见 `references/anti-patterns.md`。

### 4.1 启动 — 新功能

```
## 任务：<功能名>

### 背景
<1-2 句。项目是什么，这个功能放在哪里？>

### 需求（用户视角，不含技术细节）
<用户将体验到什么>

### 约束（违反即重做）
- <技术约束> — 如：不引入新 AI 模型，复用现有 LLM
- <架构约束> — 如：Python 脚本只做纯计算
- <禁止项> — 如：不能用硬编码匹配规则

### 验收标准（DoD）
- <可验证的完成定义> — 如：`python main.py` 端到端跑通并输出预期结果
- <质量线> — 如：现有测试全绿；新功能有对应测试
- 完成的唯一标志：真实执行证据，而非「已实现」的声明

### 交付标准
- <代码质量> — 如：注释用英文
- <文档> — 如：国际化文档用英文

### 设计风格
<一句话> — 如：精简但不粗糙，优先复用现有模块

### 执行方式
先给方案概览（不要代码）。我确认方向后再开始实现。
```

### 4.2 对齐 — 编码前确认

```
写代码之前，先给出：
1. 方案概览（2-3 句）
2. 受影响的文件和模块（新增 vs 修改）
3. 关键设计决策及理由（有 2+ 个可行方案时附简表对比：
   复杂度/风险/可调试性——简单性是显式标准，见原则 2.6）
4. 潜在风险

我确认后你再开始实现。
```

**可跳过的场景**：单函数改动、加参数、琐碎修复。

### 4.3 纠偏 — 修正方向

```
<方法/模块> 的当前实现用了 <方案>，不满足要求。

不能：<具体禁止项>
原因：<一句话>

应该是：<正确方向或原则>
参考：<如有类比，如「类似 X 的处理方式」>

先检查现有代码：
- 若已符合：指出在哪里
- 若不符合：修改并报告改了哪些文件/函数
```

**最小改动原则**：只动与当前需求直接相关的代码。不重构无关代码。不加未要求的功能。

### 4.4 继续 — 长任务推进

| 情境 | 提示词 |
|------|--------|
| 方向明确、风险低 | `继续。` |
| 推荐（防漂移） | `继续，下一步是 <步骤>。遇到阻碍告诉我，不要自作主张改变方向。` |
| 长任务、分批执行 | `已完成：<部分>。本轮只做：<本轮目标>。其余等我确认后继续。` |

### 4.5 验证 — 测试与验收

```
测试 <模块/功能> 并生成测试报告。

测试要求：
- 覆盖：核心功能列表
- 路径：正常路径 + 边界值 + 错误场景，每个错误分支至少一个用例
- 方法：真实执行（非 mock），验证实际输出
- 环境：环境/显示类问题不阻塞测试，跳过并最后汇总

测试纪律：
- 测试失败 = 实现有问题。修实现，不许改测试（删断言/放宽预期 = 违规重做）
- 报告只收真实执行结果。没有命令 + 输出 = 未测试

报告要求：
- 格式：Markdown
- 内容：用例 / 结果 / 通过率 / 问题分析 / 改进建议
- 文件名：<模块>_test_report.md
- 结尾一句话：是否可上线？
```

### 4.6 审查 — 代码审查

```
审查 <文件/模块>，重点关注：
1. 不该硬编码的逻辑被硬编码
2. 重复代码或冗余 import
3. 已废弃 API
4. 错误处理完整性
5. 项目约束符合性：<一行约束>

问题分级：P0（必须修）/ P1（应该修）/ P2（有则更好）。
```

### 4.7 调试 — 排查问题

```
## 任务：调试 <问题现象>

### 现象（用户视角）
<期望行为 vs 实际行为 + 复现步骤>

### 纪律
- 先复现，再修复。无法复现时，先解决复现问题
- 一次只验证一个假设，禁止同时改多处
- 修复后必须能说清根因。说不清根因 = 没修好

### 步骤
1. 复现：最小步骤稳定复现
2. 隔离：定位到具体文件/函数/分支
3. 假设：列出 2-3 个可能根因，按可能性排序
4. 验证：逐一验证（加日志 / 最小实验）
5. 修复：只改根因相关代码
6. 确认：原复现步骤通过 + 按结构 6.3 级联验证检查关联功能

### 输出
根因 → 修复方案 → 改动文件 → 验证证据（真实执行输出）
```

### 4.8 走查 — 用户体验审查

```
以真实用户视角走查 <功能>：
- 空状态：无数据时用户看到什么？有引导吗？
- 加载态：等待时有反馈吗？会像死掉一样吗？
- 错误态：报错文案用户能看懂、知道下一步怎么办吗？
- 边界：空输入、超长输入、特殊字符、极端值的表现
- 反馈闭环：每个操作有明确的结果反馈吗？

输出：问题清单（位置 + 用户感受 + 建议），按对体验的伤害排序。
```

### 4.9 交付 — 发布检查

```
## 任务：交付检查 <模块/功能>

以「全新用户 + 全新机器」的标准审计：
1. 硬编码路径 / 环境假设（绝对路径、特定 OS、预装依赖）
2. 步骤顺序依赖（必须按特定顺序操作才能成功？）
3. 错误信息友好度（按 4.8 走查标准）
4. 首次运行端到端可用？
5. 残留物：调试代码、注释掉的代码、TODO、示例数据

输出：
- 问题按 P0/P1/P2 分级，每项：位置 + 影响 + 建议修复
- 结尾一句话结论：是否可交付
```

**接受改动的习惯**：让 AI 展示完整 diff 而非只说「改好了」。看 diff 是最后一道质量闸门——范围蔓延（D14）几乎总能在 diff 里第一眼发现。
