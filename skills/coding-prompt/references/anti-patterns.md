## 5. 反模式速查

常见情境的弱 → 强转换。「详见」列指向展开说明，此处保持一行一击。

| 情境 | 弱提示词 | 强提示词 | 详见 |
|------|----------|----------|------|
| 新功能起点 | `实现 X` | `我的日常场景：<我实际怎么用它>。从这个使用场景设计，不是从技术实现设计。` | 原则 2.2 |
| 代码太复杂 | `简化一下` | `剥到核心功能。删除所有未用代码。不过度抽象。` | 原则 2.6 |
| AI 跑偏 | `错了，重做` | `停。方向错了——我要 X 不是 Y。重新理解需求。不要保留之前的代码。` | 模板 4.3 |
| AI 改太多 | `小心点` | `只改 <文件/函数>。不动其他文件。报告改了什么。` | 模板 4.3 |
| 输出太啰嗦 | *(隐式)* | `只要代码。除非有关键决策需要确认，否则不解释。` | 模式 3.4 |
| 出错卡住 | *(隐式)* | `出错就记录并继续。最后汇总所有问题。` | — |
| 命名/冲突风险 | `实现 X` | `设计 <规则> 时构造边界冲突用例：特殊字符、等价输入、极端情况。先修风险再继续。` | 结构 6.5 |
| 有改进想法 | `改成 X` | `我有个想法：<X>。先评估：逻辑成立吗？有副作用吗？我确认前不动代码。` | 原则 2.5 |
| 清理旧代码 | `删掉 X` | `<功能> 已完全移除。全库搜索残留代码、import、注释、文档引用。删除前列清理清单。` | 结构 6.4 |
| AI 说「做完了」 | `很好` | `给证据：跑起来给我看输出，或指出哪个文件/函数实现了它。` | 原则 2.7 |
| AI 说「改好了」 | `好的` | `展示完整 diff。我看过 diff 才算接受。` | 原则 2.7 |
| 交付了占位实现 | *(漏掉)* | `这是骨架不是实现。把所有 TODO/pass/占位/示例数据换成真实逻辑。不许有 stub。` | 清单 D12 |
| 规则匹配更佳时用了硬编码 | `提高准确率` | `这个必须 LLM 原生。不许硬编码规则、关键词表、打分算法。LLM 的理解力足够。` | 原则 2.8 |
| 局部优化陷阱 | `再调调 X` | `<X> 已经改了多轮。停——是不是 <方案/架构> 本身错了？从 <使用场景> 重新分析。不许继续打补丁。` | 结构 6.2 |
| 只测 happy-path | `写测试` | `覆盖：正常路径 + 边界值 + 错误场景。每个错误分支至少一个用例。` | 模板 4.5 |
| 为过测试弱化测试 | *(漏掉)* | `不许为通过测试而删断言/放宽预期。测试失败 = 实现有问题，修实现不修测试。` | 清单 D16 |
| 伪称已运行 | *(漏掉)* | `执行测试并贴出命令与真实输出。没有执行输出 = 未完成。` | 清单 D15 |
| 断言实现而非行为 | *(漏掉)* | `断言行为（输入→输出），不断言内部实现细节。` | — |
| 发布前审计 | `检查 bug` | `假设我是全新用户。审计：硬编码路径？环境假设？步骤顺序依赖？错误信息友好度？全新机器能端到端跑通吗？` | 模板 4.9 |
