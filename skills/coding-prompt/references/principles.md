## 2. 核心原则

这些是基础性规则。它们不是模板——是评估每一条编程提示词的透镜。

### 2.1 用「不能」替代「应该」

AI 对禁止性指令的遵循精度远高于建议性指令。「应该」制造坡度，「不能」制造悬崖。

**规则**：尽可能把每个「应该」替换为具体、可量化的「不能」。

- 弱：`代码应该简洁` → 强：`不能引入新依赖。不能创建只用一次的工具类。`
- 弱：`结构应该清晰` → 强：`嵌套不能超过 3 层。函数不能超过 50 行。`
- 弱：`算法应该更智能` → 强：`不能用硬编码匹配规则。必须用 LLM 判断。`

**量化很重要**：「不要太长」仍然模糊；「每个函数 50 行以内」才可执行。

### 2.2 场景先行

单项影响最大的模式。AI 默认从技术实现出发设计（扫文件 → 解析 → 存储 → 索引），但最好的设计从用户实际使用方式出发。

**规则**：功能提示词的第一条约束应该是使用场景，而不是技术需求。

- 弱：`实现一个文件快照系统，支持保存、恢复和 diff。`
- 强：`我的日常流程：编辑文档时想存个快照，之后能看到变更历史并恢复到某个版本。基于这个场景设计。`

**原因**：AI 记忆里有 100 种实现方案。没有场景锚点，它会选「最通用/最强大」的——通常过度设计。有了场景，它会选「最贴合」的——通常更简单更好。

### 2.3 给约束，不给实现细节

定义**是什么**和**边界在哪**，让 AI 决定**怎么做**。

**规则**：约束只规定存在性和边界，绝不指定具体函数名、类层次或文件结构——除非有已验证的理由。

- 好：`必须有一个存放所有模板元数据的地方。LLM 读取元数据并选择合适的模板。`
  → AI 选择了 `meta.json`——最优解，而非被规定的。
- 坏：`创建 TemplateMetadataManager 类，带 get_matching_template() 方法。`

**例外**：与现有代码集成时，为保持一致性而约束命名/结构是合理的。

### 2.4 先诊断现状，再采取行动

永远不要假设当前状态。要求 AI 先检查再动手。这防止修改不需要修改的东西，或破坏本来就正确的东西。

**规则**：任何纠偏动作，以诊断性问题开头。

- 弱：`把匹配算法改成 LLM 驱动。`
- 强：`检查当前匹配算法是否已经是 LLM 驱动。如果是，指出在哪里。如果不是，按以下原则修改：…`

**效果**：改动范围更小、副作用更少、避免不必要的重构。

### 2.5 实现之前先质疑需求

AI 默认做加法——用户必须主动扮演减法角色。

**规则**：任何非平凡功能，实现前回答三个问题：
1. 为什么需要这个？
2. 最简单的替代方案是什么？
3. 如果去掉它会破坏什么？

**同时适用于自己的想法和 AI 的提案。** 一句「为什么需要这个」消除的复杂度，超过任何优化环节。

### 2.6 把简单作为显式标准

面对多个技术选项，AI 会选最「强大/灵活/通用」的。简单必须写进评估标准——它永远不会是默认值。

**规则**：面对技术决策时，显式加入简单性标准：
- 实现复杂度（代码行数、依赖数量）
- 可调试性（问题能否快速定位？）
- 可理解性（新团队成员能否看懂？）
- 无谓抽象（是否过度设计？）

**默认**：选最简单的选项，除非有具体的技术理由不这么做。

### 2.7 验证先于信任

「已实现」≠「能运行」≠「满足需求」。

**规则**：
- **事前**：开工前定义可验证的验收标准（DoD），而非事后。
- **事后**：AI 声称完成时，要求它**自行执行验证并贴出真实输出**——命令 + 实际结果，而非转述。Agent 时代 AI 自己能跑命令，让它跑给你看，比「我相信你做完了」强一个量级。
- **零信任**：没有执行证据的「完成」一律按未完成处理。

相关失败模式（假完成/伪称已运行/弱化测试）见 `references/checklist.md` D12–D16。

### 2.8 LLM 原生优先于规则匹配

训练数据中传统算法代码占比很高，导致 AI 系统性偏向规则/硬编码方案——即使 LLM 自身能力能产出更好、更简单、更稳健的结果。

**常见表现**：
- 用硬编码关键词列表做模板匹配，而不是 LLM 语义理解
- 用 if-else 链或正则做分类，而不是 LLM 判断
- 用字符串操作做内容分析，而不是 LLM 理解
- 用查找表做决策，而不是 LLM 推理

**规则**：当功能涉及对内容的理解、匹配、分类或决策（文本、代码、自然语言）时，显式评估：**LLM 能否直接做？** 能则强制 LLM 原生实现。

- 弱：`提高模板匹配准确率。`
- 强：`模板匹配必须由 LLM 读取模板元数据后决定用哪个。不能用硬编码关键词、正则或打分规则。LLM 的理解能力足够——不要额外加算法模型。`

**例外**：确定性操作（文件 I/O、数据格式转换、配置解析）适合规则方案，LLM 判断不增加价值。
