# 结构与边界类模式（4 条）

> 本组模式主要迁移到 **P（扩展/配置方式）**、**T（工具注册）**、**L（安全边界）**、**E（执行循环）**。
> 每条含「核心思想 / 可迁移层 / 案例 / 何时不用 / 对照问题」。对照问题是抛给用户的，不是答案。

---

### Dependency Injection（依赖注入 / 微内核）· 来源：软件工程

**核心思想**：内核极薄，只负责装配，不承载业务能力。能力由外部组件注入，组件间通过声明式依赖关联。理想情况支持**可逆注册**：组件卸载时，它注册的服务、事件、副作用一并回滚。

**可迁移到**：P（扩展方式）、T（工具注册）

**案例**：DeepSeek Harness 的 Cordis 内核（插件加载/卸载/依赖，能力都在插件里，内核不承载 agent 能力）。

**何时不用 / 代价**：多一层间接 → "这个能力从哪来"难以顺藤摸瓜；需要容器/装配与生命周期管理；过度 DI 会催生"注解与配置迷宫"。**不要**在依赖少且稳定、一次性原型、没有"运行时替换能力"真实需求时用——"可插拔"要先问是不是真有人要插。

**对照问题**：你的 harness 里有没有"特权内核"？用户想替换某个能力（甚至替换执行循环）时，需要改内核吗？组件卸载后它的副作用会自己清理吗？

---

### Declarative Configuration（声明式配置）· 来源：DevOps / 基础设施

**核心思想**：用配置（YAML/JSON/schema）描述"想要什么状态"，而非用代码写"怎么做"。配置可 diff、可版本化、可覆盖（patch/overlay），运行时照着配置执行。

**可迁移到**：P（配置方式）、T（工具装配）

**案例**：DeepSeek Harness 的 cordis.yml / patch（可替换任意配置行）；OpenClaw 的可视化配置 + hot-reload。

**何时不用 / 代价**：表达力有天花板 → 复杂逻辑塞不进配置时，会逼出"配置里的图灵完备 DSL"或逃生舱，反而更难懂；配置本身成了需要测试/校验/schema 版本化的"代码"。**不要**在行为高度动态、每次逻辑都不同、或配置项寥寥无几时用。

**对照问题**：你的用户"配置一个 agent"是写代码还是写配置？团队想覆盖某个默认行为时，需要 fork 源码还是改一行配置？声明式与命令式的边界划在哪？

---

### Graph State Machine（图状态机）· 来源：工作流 / 编排

**核心思想**：用"图"显式声明系统的状态与流转：节点是状态/步骤，边是带条件的迁移。状态显式、可检查点、可恢复，避免隐式控制流。

**可迁移到**：E（执行循环）、S（状态）

**案例**：语言框架的图编排（注意：属"模式来源"，**非** harness 案例）；许多 harness 用状态机驱动 turn/step 生命周期。

**何时不用 / 代价**：图要预先枚举节点与边 → 流程不可枚举时硬塞进去很别扭；节点/边一多，图本身成了维护负担；还需图执行器 + 检查点存储的额外基建。**不要**把三行的直线流程画成状态机。

**对照问题**：你的执行流程是"隐式写死在循环里"还是"显式声明成图"？需要条件分支、回退、检查点恢复时，哪个更容易验证？

---

### Capability Security（能力安全 / 最小权限）· 来源：安全

**核心思想**：不按"身份"授权，按"能力"授权。每个主体只拿到完成任务所需的最小能力集，能力不可越界、不可伪造。最小权限要在**结构层强制**，而非只在 prompt 层"请求"模型配合。

**可迁移到**：L（生命周期钩子/安全）、T（工具注册）

**案例**：OpenClaw 的 Reader/Actor 双代理权限分离（工具级 ACL，抗 prompt 注入）；Claude Code 的权限模式（allow/ask/deny）+ PreToolUse hook deny。

**何时不用 / 代价**：能力粒度要设计——过粗失去意义、过细难管理；授予/传递/撤销链路复杂；"为什么没权限"排障成本高；需要可信的能力分发与校验。**注意**：原型期可暂缓，但**一旦面向真实用户或接外部输入就必须补上——这不是可选项**。

**对照问题**：你的工具权限是按"整个 agent"给，还是按"子任务/子代理"细分？安全边界靠 prompt 提示还是结构强制？模型被注入时，结构层能不能兜住？
