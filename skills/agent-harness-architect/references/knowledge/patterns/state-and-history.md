# 状态与历史类模式（4 条）

> 本组模式主要迁移到 **S（状态存储）**、**V（评估/回放）**、**C（上下文）**。
> 每条含「核心思想 / 可迁移层 / 案例 / 何时不用 / 对照问题」。对照问题是抛给用户的，不是答案。

---

### Event Sourcing（事件溯源）· 来源：数据库 / 软件工程

**核心思想**：不存"当前状态"，只追加存"发生了什么事件"。状态由事件流重放推导。事件流是不可变的单一真相源，天然支持审计、回放、时间旅行、fork。

**可迁移到**：S（状态存储）、V（评估/可回放）

**案例**：DeepSeek Harness 的 append-only session log（"model-visible means logged"）；Codex Harness 的 Item/Turn/Thread 事件流。

**何时不用 / 代价**：事件流只增不减 → 存储持续增长；读当前状态要回放（慢），通常再配快照或 CQRS；事件 schema 落盘后难改 → 版本演化负担；调试更绕。**不要**为 CRUD 场景套事件溯源。

**对照问题**：你的状态是"存当前值"还是"存发生了什么"？若会话需要可回放、可 fork、可审计，把"日志"提升为"唯一真相源"会带来什么？

---

### Immutable State（不可变状态）· 来源：函数式编程

**核心思想**：状态一旦创建不可修改，任何"变更"都产生新版本。旧版本永远可回溯、可对比、可审计，天然支持并发与快照。

**可迁移到**：S（状态存储）、C（上下文）

**案例**：Hermes Agent 的"文件即记忆"（Markdown 文件作为可审计状态）；事件溯源本质是"状态只增不改"的延伸。

**何时不用 / 代价**：写放大（改一点要复制结构）→ 内存与 GC 压力，需持久化数据结构（结构共享）才不慢；从可变迁移到不可变重构成本高。**不要**在状态巨大且高频局部更新、内存受限时用。

**对照问题**：你的状态是"原地改写"还是"只增不改"？需要"回到 10 轮之前"或"审计某次变更"时，原地改写还做得到吗？

---

### CQRS（命令查询职责分离）· 来源：软件工程 / 数据库

**核心思想**：把"写"（命令，改变状态）与"读"（查询）分成两条路径、两套模型。写路径保证一致性，读路径为查询优化，各自独立演化。

**可迁移到**：S（状态存储）、V（评估）

**案例**：Hermes Agent 的自修复验证（执行路径与校验路径分离）；多数 harness 的"执行日志（写）"与"评估/回放（读）"天然分离。

**何时不用 / 代价**：引入最终一致性（读模型滞后）、双份存储与同步管道、运维复杂度上升；小系统里是过度工程。**不要**在读写模型本就一致、或要求"读到刚写入"的强一致读时用。

**对照问题**：你的"执行"和"验证/评估"是同一套路径还是分离的？如果评估需要不被执行污染的数据源，读写分离能带来什么？

---

### Reversible Computation（可逆计算 / 可逆副作用）· 来源：编程语言

**核心思想**：每个操作都有明确可逆的"逆操作"，副作用可精确回滚。系统"卸载即清理"、热插拔无残留，长期运行不积累状态污染。

**可迁移到**：L（生命周期钩子）、P（扩展方式）

**案例**：DeepSeek Harness 的 Cordis 时间维可组合性（插件卸载时彻底注销关联服务与事件监听器）。

**何时不用 / 代价**：要为每个副作用写逆操作/补偿 → 代码与存储复杂度上升；很多副作用本质不可逆（邮件已发、款已扣），只能"补偿"而非真回滚；逆操作易写错且难测。**不要**在副作用天然不可逆、且补偿逻辑比正向逻辑更复杂时用。

**对照问题**：你的插件/组件被卸载后，它注册的服务、监听器、副作用会自动清理吗？如果要求"热插拔不留残留"，每个副作用都有逆操作吗？
