# 效率与缓存类模式（6 条）

> 本组模式主要迁移到 **C（上下文）**、**E（执行循环）**、**T（工具披露）**、**S（状态/复用）**。
> 每条含「核心思想 / 可迁移层 / 案例 / 何时不用 / 对照问题」。对照问题是抛给用户的，不是答案。
> 与「模型组合」的分界线：模型组合管**选哪个模型做这一步**，本组管**这一步能不能不重算、能不能同时跑、能不能让用户少等**。

---

### Prefix-Stable Context（前缀稳定上下文）· 来源：推理工程 / CDN 缓存

**核心思想**：把上下文切成**稳定前缀区**（系统指令、工具定义、项目规则、已发生的历史）与**可变尾部**（检索片段、动态工具子集、当前输入）。轮次之间只允许**追加**，不允许重排、重渲染、重注入易变值（时间戳、随机 id、未排序的集合）。推理侧按**最长公共前缀**复用缓存，前缀一动，从变动的那个字节起全部重算——你重排了一次工具列表，前面三万 token 的账就得重付一遍。

**可迁移到**：C（上下文布局）、E（重试与轮次重建）、T（工具披露顺序）

**案例**：主流推理 API 把「命中的前缀 token」与「重算 token」分开计价（倍数与门槛以厂商实时文档为准，**此处不写死倍数**）。本知识库内的反对照：Codex Harness 的上下文压缩、Claude Code 的自动 compaction，都是典型的「前缀整体重写」事件。

**何时不用 / 代价**：为稳定牺牲新鲜度（规则或工具变了要版本化 + 显式失效才能生效）；牺牲「按用户 / 按请求个性化的系统提示」（个性化内容须下沉到尾部）；自托管且推理栈无前缀复用时收益为零；为了省字节把易变内容硬塞进前缀（比如把时间戳写进 system 指令）是自相矛盾。**不要**在会话极短（前缀本身没几百 token）时为它付出工程复杂度。

**对照问题**：你每一轮的 prompt 是「上一轮 + 追加」还是「重新拼一遍」？系统提示里有没有时间戳 / 随机 id / 未排序集合？工具表是固定顺序，还是每次按需重排？压缩一次，后面多少 token 要跟着重算？

### Cache-Aware Invalidation（缓存感知的失效预算）· 来源：存储系统 / 编译缓存

**核心思想**：凡是**重写上下文**的动作都有缓存代价——重写点之后的全部 token 失去复用。因此把「失效预算」当成与 token 预算并列的一等预算：规定一轮内允许几次全量重写、触发条件是什么、重写粒度是整体还是分段（分段压缩优于整体压缩）。**看得见的省（压缩后 token 变少）往往盖住看不见的赔（缓存整段失效）**，两者必须同表核算。

**可迁移到**：C（压缩策略）、E（重试与降级）、V（评估要不要单独起一轮）

**案例**：DeepSeek Harness 的 80% 水位压缩（留最近 16% + LLM 摘要）、Claude Code 的「长会话显式 /compact」——两者都应附一句代价注释；Codex Harness 的上下文压缩（相对无压缩基线 token 减 83.3%）同理，收益与失效需放在一起看。**换模型也是失效事件**：跨模型的缓存不共享，级联升级时旧前缀一并丢弃。

**何时不用 / 代价**：分段 / 增量压缩实现复杂，要维护段边界与依赖；过度推迟压缩会让单次请求变贵并逼近窗口上限；降级切换模型时谈不上省，只能选「快速失败并保持正确」。**不要**为了保缓存把明显该压缩的请求硬扛到窗口溢出。

**对照问题**：一次压缩会废掉多少已缓存 token？能否只压中段、保住头部？失败重试是续跑还是重建（重建 = 主动放弃缓存）？级联升级这一升高，缓存是不是跟着一起丢了？

### Deterministic Serialization（确定性序列化）· 来源：构建可复现性 / 编译器

**核心思想**：同一语义内容必须序列化成**同一字节串**——集合先定序、字典 key 定序、空白与换行统一、数值格式统一、派生 id 用稳定哈希而非随机数。缓存按字节前缀匹配，**语义相同但字节不同 = 一个 token 都命中不了**，这是最常见、也最容易被忽视的漏钱方式。

**可迁移到**：C（消息组装）、T（工具 schema 装配）、S（状态快照与回放）

**案例**：Codex Harness 的动态工具加载（按需搜索 schema 避免 prompt 膨胀）——若每次「按需」挑出的子集顺序不同，省下的 prompt 会被前缀失效赔回去；相比之下固定顺序 + 尾部追加更安全。同一会话重放时的 message 规范化（role 顺序、空白、数值格式）同理。

**何时不用 / 代价**：排序开销随工具数量上升（量小可忽略）；「按相关性动态排 tool」的收益是否盖得住失效，需实测而非拍脑袋；团队没有统一序列化约定时难以长期维持。**不要**为了字节完美而给每个字段写自定义比较器，工程成本会吃掉收益。

**对照问题**：两次语义相同的请求，字节串一样吗？工具 schema 是每次动态挑五个塞进去，还是固定序 + 尾部追加？你们有没有一条「谁也不许改 serialization」的硬约定？

### Result Memoization / Reuse（结果复用与幂等缓存）· 来源：缓存系统 / 数据库

**核心思想**：把昂贵且确定的中间产物缓存起来——同参数工具调用的结果、同一文件同一版本的解析结果、同一段会话的摘要。用**内容寻址键**（输入指纹 + 版本），并先于缓存实现定好失效条件（文件版本、TTL、权限变更）。

**可迁移到**：T（工具结果入窗前先过缓存）、C（大对象写文件只回引用）、S（快照复用）

**案例**：构建系统的产物缓存（输入指纹不变则不重跑）；本知识库 CLM-8B 条目的嵌入缓存——候选文本只嵌入一次，缓存冷 106 token / 热 38 token（官方自报），是「复用带来的数量级差异」的现成量化参照。

**何时不用 / 代价**：脏缓存比不缓存更危险——读到的旧数据会被当成事实引用（须与 S 层「证据版本绑定」联用）；写操作与非幂等操作**禁止**缓存；隐私数据入缓存要脱敏与按用户隔离；命中率低的场景维护成本大于收益。**不要**缓存「看着很像但其实是读远程状态」的调用而拿不出失效条件。

**对照问题**：同一个 grep / 同一网页抓取，一轮里被调用了几次？命中缓存拿到的结果，凭什么证明它还有效？哪些写操作被误放进了可缓存那一栏？

### Wall-Clock Budget & Bounded Parallelism（墙钟预算与有界并行）· 来源：操作系统调度 / 并发控制

**核心思想**：用户感知的是**墙钟时间**，不是算了多少 FLOPs。把「一轮总共能花多少秒」摊到各串行环节，能同时跑的必须同时跑（互不依赖的工具调用、可并行的子请求），并行度**必须封顶**（有界池），否则成本、上下文和下游配额会同时失控。

**可迁移到**：E（轮内调度）、T（可并行 / 独占标记）、P（编排与扇出）

**案例**：DeepSeek Harness 的工具「可并行 / 独占」分类 + 有界并行池（≤10，读写按依赖调度）；Claude Code 的 per-session web / subagent 硬上限（既防失控也防把上下文撑爆）。

**何时不用 / 代价**：并行会让日志交错、复现变难（可观测性要跟着升级）；依赖没理清就并行 = 竞态；扇出无界会让 token 与上下文同时失控；下游限流会把并行收益原样打回去。**不要**为了并行把有先后依赖的步骤硬拆。

**对照问题**：一轮里哪几步本来可以同时跑？并行上限由什么定（下游配额 / 依赖 / 上下文容量）？并行里的部分失败怎么合并结果？

### Streaming & Interruptibility（流式输出与可中断执行）· 来源：人机交互 / Web 性能

**核心思想**：体感的「快」由**首字节延迟（TTFT）**与**可控感**决定，而非总耗时。流式增量输出让用户在第一个 token 就有响应；中断点必须落在确定的回合边界，且取消时要交出「已经发生了什么副作用」的清单——能停不算本事，停得干净才算。

**可迁移到**：E（可中断 turn）、L（审批与人在回路）、V（流式下的验收点）

**案例**：Codex Harness 的 Item/Turn/Thread 生命周期事件（started / delta / completed）天然支撑流式渲染，配合 interruptibility（可中断、可改运行时状态）；Claude Code 的 hooks 与 plan 模式把「能不能继续」做成确定性拦截点。

**何时不用 / 代价**：流式与「必须整体核验后才能交付」直接冲突（先验证再吐会牺牲 TTFT）；中途取消要处理已发生副作用，天然不可逆的写操作（邮件已发、款已扣）只能补偿不能回滚，必须显式告知；协议与 UI 要支持增量渲染。**不要**为了流式而放弃「输出前最后一次校验」这条安全底线。

**对照问题**：用户多久能看到第一个字？中途取消时，已经发生的写操作怎么办？「眼看着它在跑」这件事，在你的设计里由谁负责？
