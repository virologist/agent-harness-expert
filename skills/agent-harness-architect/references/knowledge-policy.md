# 自进化知识库政策（references/knowledge-policy.md）

> 唯一定义处：知识库的**位置、读取、入库、防污染、容量与替代**规则都在这里。SKILL.md §0-B 只放路径指针。

## 一、两套位置：包内基线 + 团队 wiki 底座

> **团队语境**（本包内嵌于 agent-harness-expert 专家团）：知识统一沉淀到 wiki 底座，架构师的进化就是团队的进化。独立使用本 skill 时，把本节的「wiki 底座」替换为外部进化库 `$WORKBUDDY_CONFIG_DIR/agent-harness-knowledge/`，其余规则不变。

| | 包内（只读） | 团队 wiki 底座（可写） |
|---|---|---|
| 路径 | `<SKILL_DIR>/references/knowledge/` | `<项目>/.wiki-creator/`（主理人经 wiki-creator 维护） |
| 角色 | 随包分发的**基线** | 团队自进化的**增量** |
| 读写 | 只读 | 主理人写入 |

- **读取顺序：先底座、后包内**（index 与条目文件都按此顺序）。底座已有编译产物时以其为准，包内同名条目被底座覆盖。
- **架构师不直接写知识库**：把过防污染标准的「拟入库条目」随设计回传主理人，由主理人在阶段收尾经 wiki-creator 编译进底座；写入与读取必须是同一套（都指底座）。
- `scripts/knowledge_lib.py`（独立使用时管理外部进化库）：`status` 报告两套路径现状；`init` 初始化外部库（复制包内 index 作起点）；`ingest <文件>` 把新条目收录进外部库并刷新其索引行——团队语境下不用。

**关键纪律**：写入位置与读取位置必须是同一套。历史上曾出现"写 cwd、读包内"导致进化产物永远读不到的断链，禁止回退。

## 二、自进化五步闭环（按需触发，不每次调用都搜）

| 步 | 动作 | 规则 |
|---|---|---|
| 1 触发 | 遇到知识库盲区（用户提未知框架 / 问最新框架） | 按需，不主动频繁搜索 |
| 2 搜索 | 官方 repo、论文、官方文档 | 一手来源优先 |
| 3 质量门控 | 来源分级 + 防污染（见下） | 非官方一票否决 |
| 4 解析+确认 | 按模板整理 → 展示"拟写入/拟更新" | **默认不静默写**，用户确认才落盘 |
| 5 入库+反哺 | 团队语境：整理成条目**随设计回传主理人**，由主理人经 wiki-creator 编译进 wiki 底座；独立使用：写入外部库并刷新其 index.md | 入库前查重（同框架更新而非重复） |

**搜索容错（MUST）**：网络检索是外部依赖，失败/限流/超时属正常现象。单次失败最多重试 2 次；连续 3 次失败即放弃入库这一步，**继续推进架构设计本身**，并在交付说明中标注"本次未做知识库扩展（原因：网络不可用）"。
**知识库自进化永远是可选增强，不是交付设计文档的前置条件**——绝不因为搜不到新资料就不产出架构设计。

## 三、防污染（入库标准，唯一定义处）

- **"官方"三类来源**：① 著名大厂（官方 GitHub org / 官网 / 官方文档）；② 优秀创业团队（官方仓库 + 官方文档 + 可查机构背景，三者齐备）；③ 权威学术（论文有作者机构 + DOI）。
- **一票否决**：个人博客、二手解读、AI 生成摘要 → 拒绝；官方但无法交叉验证 / 追溯 → 拒绝。
- **置信分级**：`verified`（官方可追溯）可入库、可作高可信建议；`unverified` 不进 core、只作待核线索。
- 每条必带 `source` + `added` + `version` + `confidence`，可追溯、可回滚。
- **禁止推测填充**：某框架的某个维度（如执行环境）查不到，就留空或标注"未公开"，**不许按同类产品推测后当作事实写入**。

### 首次播种 vs 后期入库

- **首次播种的 5 个种子**：用户显式指定的常驻锚点，整理时参考官方信息 + 权威解读（尤其闭源框架的官方博客）。这是一次性授权。
- **后期一切入库**：严格执行上面的防污染标准，无例外。

## 四、容量分层与替代

| 层 | 容量 | 替换规则 |
|---|---|---|
| 常驻层（pinned） | 固定 5（用户指定） | 默认永不替换，除非命中淘汰判定 |
| 流动层（rotating） | ≤ 5 | 走三层替代评估 |
| core 总量 | ≤ 10 | — |

`archive/`、`inbox/`：按需创建，不保留空目录（被替代者降级 archive，官方但信息不全的候选放 inbox 待补全、不进 core）。

**替代评估（三层）**：① 准入门槛（官方 + 可追溯，一票否决）→ ② 核心价值评分（原创度 40% + 代表性 30% + 激发潜力 30%，每维 0/2/4 分）→ ③ 用户终审（对比表 + 理由，确认才替换；被淘汰者降级 archive/，不删除）。

**常驻淘汰判定（三重门槛，缺一不可，用户终审）**：① 客观失效（官方归档 / 停维护 / 弃用 / 范式被证明有缺陷）→ ② 同生态位被全面超越（同范式位三维全超，非跨范式比较）→ ③ 用户确认。skill 只输出"建议淘汰报告"，绝不自动淘汰。

## 五、条目模板（唯一定义处）

> 新增 / 更新条目时用这里的模板；写完用 `scripts/lint_knowledge.py <路径>` 校验必填字段。
> 条目 `type` 枚举：`harness` / `model`。类别字段（如生成式/决策型）为**开放枚举**：未来新增物种只加枚举值与数据行，机制不变。

### 5.1 框架条目（frameworks/core/<name>.md）

> 严格判别：**运行时宿主**（可独立启动、配置装配），不是语言框架（import 进来写代码的库）。

```markdown
---
name: <框架名称>
alias: <简称>
type: harness                      # 严格判别：运行时宿主，非语言框架
source: <官方 URL 或 DOI>
papers: ["<相关论文标题/链接，可空>"]
added: <YYYY-MM-DD>
version: <版本，如 v0.1>
confidence: verified               # verified / unverified
pinned: true                       # true=常驻层（用户指定）；false=流动层
---

## 一句话定位
<用一句话说清它是什么>

## H 六层映射
- E: <执行循环怎么实现>
- T: <工具怎么注册/接入；在哪执行（本地/沙箱/远程）；凭证是否进执行环境>
- C: <上下文怎么管理>
- S: <状态怎么存储/持久化；外部副作用是否幂等>
- L: <生命周期钩子/安全怎么做；人在回路分几档>
- V: <评估/验证怎么做；生成者与评估者是否分离>

## 范式 P
扩展方式=<插件化/嵌入式> · 配置方式=<声明式/命令式> · 部署=<单机/分布式> · 编排=<中心化/去中心化>

## 模型组合
<该 harness 是否支持多模型/模型选型/子代理分档；查不到写"未公开"，禁止推测填充>

## 原创点（框架外，重点标注）
1. <原创点一，属于框架之外的新知识才叫原创>
2. <原创点二>

## 设计启发
<这个案例在哪个维度上能给人启发、可作什么对照物>
```

> 模板里 T / S / L / V 括号中的提示语是**必答项**；查不到就写"未公开"，**禁止推测填充**。

### 5.2 模式条目（patterns/<主题文件>.md 内的 `###` 小节）

> 模式按主题合并：一个文件含 2–4 条，每条一个 `###` 小节，文件 frontmatter 记 `group` / `count` / `confidence`。

```markdown
### <模式名称>（<中文名>）· 来源：<来源领域>

**核心思想**：<解决什么问题、怎么解决>

**可迁移到**：<H 六层中的哪几层>

**案例**：<真实案例，可指向 frameworks/core/ 中的条目；没有则写"待补">

**何时不用 / 代价**：<引入它的代价是什么；什么情况下不该用——架构师的克制>

**对照问题**：<抛给用户的问题，而非答案>
```

> 「何时不用 / 代价」是**必填**：只讲优点不讲代价的模式会诱导过度设计。

### 5.3 模型条目（models/core/<name>.md）

> 模型条目是**数据层**：机制（框架问题/脚本/模板）面向能力特征，零产品名；具体模型只在这里以数据身份出现。
> 类别为开放枚举（生成式 / 决策型 / …），新物种加枚举值即可。

```markdown
---
name: <模型名称>
alias: <简称>
type: model
category: <生成式 / 决策型 / …（开放枚举）>
source: <官方 URL（文档/仓库/模型卡）>
added: <YYYY-MM-DD>
version: <版本或状态，如 early access>
confidence: verified               # verified / unverified
pinned: false                      # 模型条目默认流动层
---

## 一句话定位
<用一句话说清它是什么物种、解决什么>

## 接口形态
<怎么接入：API/本地推理/嵌入服务；输入输出形态；与四分类档位的对应关系>

## 延迟 / 成本量级
<只写量级并注明核实日期；禁止虚构精确价格。官方自报与第三方数据分开标注>

## 已验证适用域
<有来源支撑的适用场景，逐条注明出处>

## 已验证不适用域
<负结果（何时不用）——"何时不用"纪律的示范。来源分级见下>

## 降级策略
<该模型不可用（限流/故障/涨价）时的替代路径；升/降档方向>

## 设计启发
<这个条目在模型组合设计上能作什么对照物>
```

**"已验证不适用域"来源分级通则**（适用一切模型条目）：

- 负结果出自**官方自报**（官方文档/仓库/模型卡）→ `confidence: verified`，正文标注"作者自报"；
- 出自**第三方或个人来源**（博客/独立基准）→ 一律 `unverified` 待核线索（注明"待官方或可追溯来源复核"），不得进 verified 级正文。

**未收录模型处理通则**：用户点名的模型不在知识库时，不得凭训练记忆推荐或杜撰规格——① 向用户索取公开文档/官方来源，或明确标注"知识库未收录"；② 设计时按其能力特征（接口形态/成本量级/适用域）落入四分类档位；③ 条目经用户确认后按本模板入库。
