# H 框架详解（通用骨架）

> 本文件是**逻辑层**的静态参考，通篇通用，不含任何具体框架名。
> 六层名称与职责在这里定义一次；每层的**必答设计问题**是设计阶段的最低检查面，缺一项即视为未设计完。

## 一、总定义

- **Agent = 模型 + Harness**。
- **Harness = 六层功能 + 架构范式 P**。

六层功能：E 执行循环、T 工具注册、C 上下文管理、S 状态存储、L 生命周期钩子、V 评估接口。
P：架构范式，指这个 Harness 以什么风格组织起来。

模型不是 Harness 的功能层（不加第七层，一阶定义不动），但**模型是显式设计对象**：设计 Harness 时必须显式设计"什么认知步骤交给什么档位的模型"，见下节。

### 模型组合（Model Portfolio）

> 每个认知步骤都要归入四分类之一。当分档被判定为必要时，主战场是**单智能体执行循环内的步骤**；只写类别与判据，不写任何具体模型名——具体模型属知识库数据层（`knowledge/` 的 model 条目）。

**模型组合四分类**

| 归属 | 判据 | 典型步骤 |
|---|---|---|
| 确定性代码 | 答案集可枚举、可断言、无需理解 | 正则、规则、查表、路由表 |
| 决策型模型（System One） | 封闭答案集 + 高频重复 + 可按置信度行动 | 紧急度判断、工具选择、风险门控 |
| 快速低价 LLM | 需要语义理解但任务简单、容错空间大 | 分诊、中间摘要、格式转换、简单回复起草 |
| 强力 LLM | 开放推理、生成、跨步因果、最终裁决 | 主推理循环、复杂编码、评估仲裁 |

**单/多智能体三形态**（"单智能体优先"约束 agent 数量，不约束模型数量）：

- **形态 A**：单智能体 + 单模型——默认形态，大多数任务的现实主场景；落定前须经显式质疑（质疑是纪律），但质疑的合法结论可以是"确实单模型就够"。
- **形态 B**：单智能体 + 循环内多模型节点分档——**分档的主场景**（当分档被判定为必要时的首选形态）。触发条件：成本敏感 + 任务异质性强。分档是条件触发的优化，不是默认义务。
- **形态 C**：多智能体——仅当通过下方编排决策卡门禁（命中三面墙之一且形态 B 无法替代）才放行。

**必答设计问题**（先单智能体、后多智能体）

1. 执行循环里每个高频认知步骤归入哪一类？给出**任务-模型分派表**（步骤 × 档位 × 理由）——单智能体同样必须做，不是多智能体专属。
2. 每类步骤的成本/延迟预算是多少？总 token 预算如何在档位间**分配**（不是只给总量）？**评估 / 验证步骤的成本是否已在预算内**（别让它成为预算外的隐性支出）？
3. 低档模型处理不了时如何**升级**（级联条件：置信度阈值 / 失败重试次数）？高档模型被降维使用的步骤有没有识别出来（"用大炮打蚊子"）？
4. **分档是否改变了单/多智能体的结论？** 原本想靠多 Agent 实现的"专业化"（分诊/转换/核验），能否用单 Agent + 循环内多档模型替代？——能替代就不上多 Agent。若确需多智能体（已过编排决策卡第一步），再定主脑/子代理/评估者各自档位。
5. 某档模型不可用（限流/故障/涨价）时的降级链是什么？
6. 评估者档位与生成者档位的关系？（评估者可以便宜，但必须满足独立性；"便宜"不是跳过分离的理由）

## 二、六层详解（每层：职责 + 必答设计问题）

### E 执行循环（Execution Loop）

管"任务怎么拆、怎么跑、怎么停"。内部三块：策略选择器（看任务类型决定执行方式）／策略库（可用的执行模式）／运行时引擎（跑起来，管轮次上限、Token 预算、何时停）。

**必答设计问题**
1. 终止条件谁说了算？（答案必须落在 V，不是模型自评）
2. 如何防止跑飞？（轮次上限 + Token 预算 + 每节点超时，三道保险）
3. 任务结构清晰时用静态模式还是动态脚本？
4. **失败怎么回喂？** 错误是作为观察结果回到上下文，还是被吞掉？如何分类恢复（瞬时重试点 / 模型错误带纠正重 prompt / 永久走 fallback / 资源不足升级人类）？
5. **怎么识别"在原地打转"？** 连续 N 次相同工具名 + 参数指纹如何检测与打断？
6. 循环内每个异质步骤（路由/工具选择/摘要/主推理/核验）各归哪个模型档位（见总定义「模型组合」四分类）？**"整个循环同用一档模型"必须被显式质疑**（质疑是纪律，但合法结论可以是"确实同档就够"——分档不是默认义务，成本敏感 + 任务异质才触发）。
7. 策略选择器由谁实现（确定性代码 / 决策型模型 / 快速低价 LLM / 主 LLM）？低置信度如何升级到慢思考？
8. **墙钟预算与并行**：一轮的墙钟时间预算多少？哪些工具调用互不依赖可并行？并行度上限由什么定（下游配额 / 依赖 / 上下文容量）？并行中的部分失败怎么合并？
9. **流式与可中断**：是否流式输出给用户（多久出第一个字）？能否中途取消？取消时已发生的副作用如何清点（哪些可补偿、哪些不可逆）？

### T 工具注册（Tool Registration）

管"Agent 能用什么、怎么用"。

**必答设计问题**
1. 工具如何接入？接口是否标准化？
2. 是否按需筛选子集（而不是全量暴露）？活跃工具过多时如何降级？
3. **工具在哪执行？** 本地进程 / 沙箱 / 远程——写操作的影响半径划到哪？
4. **凭证是否进入执行环境？**（答案必须是"不进"；凭证走外部代理或受控入口注入）
5. **工具注册 ≠ 工具披露 ≠ 执行授权**：注册了不等于暴露给模型，暴露了不等于这次允许执行。三者如何分离？
6. 模型组件（决策型模型 / 快筛模型等）的接入形态是什么（工具 / 中间件 / 内联调用）？不可用时的降级链是什么？
7. **工具披露序列是否稳定？** 按需筛选出的工具子集，其**顺序与 schema 序列化是否确定**（顺序一变，前缀从头失效）？

### C 上下文管理（Context Management）

管"什么信息进模型窗口"。

**必答设计问题**
1. 窗口预算多少？预算如何在系统指令 / 历史 / 工具结果 / 参考资料之间**分配**（不只是总量）？
2. 用多少比例后质量开始下降？何时压缩 / 摘要？
3. 如何让 Agent 尽量留在干净上下文里（噪音下沉到子任务 / 文件）？
4. **每轮是否重新组装？**（不重新组装 = 用过时信息）**它与"前缀必须字节稳定"的裁决在 production-checklist.md C 层唯一定义**——此处只负责把它问出来。
5. **外部内容如何消毒？** 检索/网页/文件内容是否被截断并标记为"待分析数据"而非指令？
6. 决策型模型的 state 构造是否复用上下文组装结果（避免重复花 token）？
7. **上下文序列是否前缀稳定？** 稳定前缀区与可变尾部如何划分、易变内容是否已下沉到尾部、序列化与工具披露顺序是否确定？（判据与禁令清单见 production-checklist.md C 层）
8. **重写动作有没有失效预算？** 一轮允许几次全量重写、粒度能否分段？哪些昂贵且确定的中间结果可复用、失效条件是什么？（判据见 production-checklist.md C 层）

### S 状态存储（State Storage）

管"跨轮次持久化与恢复"。

**必答设计问题**
1. 存什么结构（JSON/KV/数据库）？写操作要不要经过治理（Agent 不能直接篡改）？
2. 失败后如何重新加载状态（可审计、可恢复）？
3. 并发写如何处理（WAL / 单写 / 连接池）？
4. **会话恢复 ≠ 外部行动恢复**：重新加载进度不能证明一个超时的外部请求没成功。外部副作用是否有幂等键 + 状态查询 + 恢复策略？
5. **记忆治理**：写入长期记忆的内容，可信度怎么标、属于哪个用户/项目、什么条件下失效？未验证的推测会不会被升级成事实？
6. **证据版本绑定**：一条验证结论只对被验证的那个版本有效；版本变了怎么失效旧结论？

### L 生命周期钩子（Lifecycle Hooks）

pre-invocation / post-invocation 的拦截点。

**必答设计问题**
1. 哪些动作需要拦截（鉴权、审计、策略执行、安全监控）？
2. 拦截点能不能被 Agent 绕过或修改？（"安检门"不能被绕过）
3. 面向真实用户的鉴权是否写成协议（JWT / SSO / OIDC），而非一句"校验身份"？
4. **人在回路分几档？**（自动执行 / 执行后告知 / 执行前确认 / 直接阻断）各档覆盖哪些动作？审批量大时如何降级而不失控？
5. 高危拦截是否纵深（前置 + 独立于分类器）？
6. 快筛模型的阈值与放行率怎么定？快筛模型自身面对注入输入是否稳健？

### V 评估接口（Evaluation Interface）

管"你怎么知道做对了"。

**必答设计问题**
1. 谁独立验证？Agent 说"成功"算不算数？（不算）
2. 用什么客观手段验证？成功标准是否可量化、可复现？
3. **生成者与评估者是否分离？** 评估方必须用**独立上下文**，且**看不到执行者的推理过程**，只看产物与执行记录。
4. 评估标准是否显式（不是"看起来不错"）？是否给出可操作反馈与迭代预算（防评估死循环）？
5. **工具回执 ≠ 业务事实**：HTTP 200 / 退出码 0 不代表业务对象进入目标状态——是否核对权威系统的实际状态？
6. 评测环境是否可比（同一套基础设施、数据、预算）？是否防"绕过任务而非解决任务"？
7. 评估步骤采用**验证强度阶梯**的哪一级？（阶梯只在 `production-checklist.md` 定义一次——此处只引用不重述）模型裁判是否满足独立上下文、不看推理、显式标准、迭代预算？

## 三、策略库里的执行模式

### ① 六种静态模式（直接使用）

1. **分类与执行** —— 先判断类型，再路由给对应处理。
2. **分叉与综合** —— 拆成多个子任务并行跑，最后合并结果。
3. **对抗性验证** —— 派一个专门挑错的 Agent 去审核结果。
4. **生成与过滤** —— 批量出方案，再筛选打分。
5. **锦标赛** —— 多个 Agent 竞争同一任务，两两 PK 选最优。
6. **循环直到完成** —— 不设固定轮数，跑到条件满足为止。

### ② 动态脚本模式（临时写）

任务结构不清晰时，主 Agent 自己写一段编排脚本，交给运行时执行。脚本可用三个基础命令：派一个子 Agent 去干活／并行派多个子 Agent 等全部做完／串行流水线。

---

## 四、终止条件怎么定

不管用哪种模式，最后能不能停，由 **V（评估接口）** 说了算——"我说做完了不算，Harness 验证通过才算"。同时设两道保险：**最大轮数上限 + Token 预算上限**。

---

## 五、多 Agent 编排决策卡（要上多 Agent 前逐条过）

> 单 Agent + 好工具能解决大部分任务。多 Agent 是为突破三面墙（上下文上限 / 无法专业化 / 串行执行）才引入的工具，不是默认架构。
> 分档的主战场在 E 层单智能体循环内（见总定义「模型组合」）；本决策卡只处理通过门禁后的多智能体子场景。

| 步 | 决策 | 判据 |
|---|---|---|
| 1 | **真的需要吗？** | 任务是否真的可拆分、子任务是否相互独立、并行收益是否大于协调成本？任一为否 → 单 Agent。**模型分档判据**：原本因"专业化"想上多 Agent 的需求（分诊/转换/核验子代理），能否用**单 Agent + 循环内多档模型**替代？能替代 → 单 Agent |
| 2 | **选拓扑** | 串行流水线 / 扇出-扇入 / 中心化调度 / 对等协商——按子任务依赖关系选 |
| 3 | **定委派契约** | 交付什么、允许读写什么、依据哪个版本、失败如何报告、超时多久 |
| 4 | **定隔离边界** | 子 Agent 是否独立上下文、独立工作区、独立权限（**隔离上下文 ≠ 隔离权限**） |
| 4.5 | **定模型档位** | 每个子 agent 用什么档位的模型（四分类）？低档处理不了时的升级条件是什么？ |
| 5 | **加熔断** | 超时、重试上限、无界扇出限制、单点失败如何降级 |
| 6 | **反模式自查** | 共享可变状态？无界扇出？过度分解？子 Agent 结论未经核验直接采信？ |

**委派结论的采信规则**：子 Agent 返回"没问题"只是一项**待采用的结论**，必须结合它实际检查的对象、范围与证据判断；主 Agent 负责整合与最终验收。

## 六、架构范式 P（开放决策，非封闭枚举）

P 是**开放的、多维的**架构决策集，至少含以下正交子维度（可扩展）：

| 子维度 | 两端 | 说明 |
|---|---|---|
| 扩展方式 | 插件化 ↔ 嵌入式 | 能力是否可随意增删替换 |
| 配置方式 | 声明式 ↔ 命令式 | 用配置描述，还是写代码 |
| 部署拓扑 | 单机 ↔ 分布式 | 子 Agent 是否可派到远程 |
| 编排模式 | 中心化 ↔ 去中心化 | 谁在调度 |

**范式 P 如何影响 E 层**：插件化 → 执行模式可增删替换；嵌入式 → E 层固定，只能调参；声明式 → 用户写流程配置，E 层照着执行；分布式 → 子 Agent 可派远程、状态跨节点同步。

> 这四个子维度只是**常见参考样例**，标注"非完备、可自定义"。真正的架构区分度（如"无特权内核"这类深度）不在标签能表达的范围内，需在设计中通过追问挖掘出来。
